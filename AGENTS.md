# Repository Guidelines

## Stack

- Next.js 16 App Router, React 19 with the React Compiler, TypeScript 6, Tailwind CSS v4 and shadcn/ui.
- PostgreSQL with Drizzle ORM, BetterAuth, and Zod 4 at every runtime boundary.
- React Hook Form, TanStack Query and Zustand on the client.
- Vercel AI SDK 7 with Groq, and an OpenRouter model for extension form filling when configured; separate services for LaTeX PDF compilation and OCR; SeaweedFS over the S3 API for stored files.
- Node.js 24, pnpm, Vitest, Playwright, ESLint and Prettier.

## Module organization

- `src/app`: routes. Dashboard features keep their components, `queries/`, `mutations/` and `store/` together. API routes live in `src/app/api/<feature>/`: `route.ts` handles HTTP, services hold the logic, and `validators.ts` exports Zod schemas shared with the client.
- `src/components`: shared UI primitives built on shadcn/ui.
- `src/lib`: environment validation, database, auth, logger, resume templates and shared helpers.
- `services/`: the LaTeX compiler and the OCR service, each with its own image and README.
- `extension/`: the autofill browser extension. Its scripts in `extension/src/` share limits and schemas with `src/app/api/autofill/`; `pnpm run extension:build` bundles them into `extension/dist/`.
- `scripts/`: migration, worker and container entrypoints.
- `tests/`: PostgreSQL integration and Playwright suites. Unit tests sit next to their modules.
- `migrations/`: SQL generated by `pnpm run db:generate`. Commit it with the schema change that produced it.

## Planning

Before exiting plan mode, have the plan adversarially reviewed:

1. Start a new `adversarial-review` agent rather than continuing an earlier one, so it reviews without your context. Pass it the plan file path, the user's original request, and the decisions the user has already made.
2. Check each finding against the code yourself; the reviewer can be wrong. Drop the ones that don't hold, with a one-line reason in the plan.
3. Revise the plan for the findings that hold, and ask the user any open questions it raises. If a finding forces a different approach, review the revised plan the same way.

## Before finishing a task

Run these and fix every error and warning before reporting a task as done:

```sh
pnpm run format
pnpm run lint
pnpm run typecheck
pnpm run test
```

## Guidelines

- Comments say what the code can't: why it was done this way, a constraint, a tradeoff, a compatibility concern. Don't narrate what the next line does or restate a name. Keep tool directives and required annotations.
- Follow the patterns in neighboring files and reuse existing helpers before writing new ones.
- Fix the cause of a lint or type error instead of silencing it: no `any`, and no `eslint-disable` or `@ts-expect-error` without a comment explaining why.
- Treat request bodies, JSON and model output as `unknown` until a Zod schema validates them.
- Add or update tests when behavior changes.
- Update the README and `docs/` when behavior, commands or environment variables change.
- Never commit secrets or bake them into container images.
- For UI work, follow the design system in `.claude/skills/design-system/SKILL.md`.
